# Журнал технических решений

Файл ведётся по шагам плана: что сделано и почему выбрано именно такое решение.

## Шаг 1. Скелет проекта, Docker, Makefile, .env.example

- Инфраструктура (Makefile, ci.yml, .golangci.yml, multi-stage Dockerfile, compose с healthcheck Postgres, .gitignore, .gitattributes, LICENSE) перенесена из `go-price-tracker` и адаптирована под домен: бинарник `parser` → `bot`, креды `tracker` → `consultant`. Проверенная оснастка — не переписываем ради переписывания.
- `go.mod`: `go 1.25` (а не локальный 1.26.4), чтобы совпадать с `golang:1.25-alpine` в Dockerfile и `go-version: "1.25"` в CI. Go 1.26 собирает модуль, требующий 1.25, без проблем.
- Сертификат Минцифры **не хранится в git** (`certs/*.cer` в .gitignore): это бинарный артефакт, качается локально через `make cert` с единственного разрешённого URL `https://gu-st.ru/.../russian_trusted_root_ca.cer`. В репозитории — только `certs/.gitkeep`, чтобы каталог существовал для `COPY certs/` в Dockerfile. Проверено: PEM, subject/issuer = Russian Trusted Root CA (self-signed корень).
- Dockerfile копирует в образ `knowledge/` и `certs/`: и база знаний, и сертификат читаются с диска на старте. Шаг `make cert` добавлен в CI перед `docker build`, иначе `COPY certs/` упадёт.
- `.env.example` — только плейсхолдеры. Переменные разбиты по блокам; критичные для конкретного `LLM_PROVIDER` секции помечены. `GIGACHAT_INSECURE_SKIP_VERIFY` документирован как крайний фолбэк с явным «никогда в проде».
- В compose у `app` нет volume для вывода (в отличие от price-tracker): консультанту нечего писать на хост, весь вывод — в Telegram и в БД.

## Шаг 2. Конфиг из ENV и slog

- `config.Load()` копит проблемы в срез и возвращает одной ошибкой — за один запуск видно весь список недостающих переменных, а не по одной.
- **Провайдер-специфичная валидация.** Ключи GigaChat обязательны только при `LLM_PROVIDER=gigachat`, ключи Yandex — только при `yandexgpt`. Требовать всё сразу заставляло бы держать в `.env` мусорные значения для неиспользуемого провайдера. Реализовано `switch` по провайдеру с отдельными `loadGigaChat` / `loadYandex`, возвращающими свои проблемы.
- Fail fast на `BOT_TOKEN`, `DATABASE_URL`, корректном `LLM_PROVIDER` и ключах выбранного провайдера. `ADMIN_TG_ID` опционален (пусто → `/reload` недоступна никому), у `SCOPE/MODEL/CERT_PATH/KNOWLEDGE_PATH/APP_ENV` есть дефолты.
- `GigaChatConfig` и `YandexConfig` — вложенные структуры, а не плоские поля: клиент получает ровно свой набор параметров, без чужих.
- `NewLogger(appEnv)` принимает окружение параметром (не читает ENV сам) — вызывается из main после Load и тестируем.

## Шаг 3. LLM-клиент: интерфейс, GigaChat, YandexGPT

- **Интерфейс `LLMClient` намеренно узкий:** `Ask(ctx, systemPrompt, userMessage) (string, error)`. Всё, что нужно боту, — задать вопрос и получить текст; подмена провайдера через ENV сводится к одной строке в фабрике `llm.New`.
- **Свой клиент на net/http, а не SDK.** Два HTTP-вызова (OAuth + chat) не окупают внешнюю зависимость, а свой код проще аудировать в чувствительных местах — TLS-пул и кэш токена. SDK упомянуты в README как опция.
- **CertPool с сертификатом Минцифры.** Цепочка TLS GigaChat подписана корнем НУЦ Минцифры, которого нет в системном хранилище. Клиент читает PEM с диска, добавляет в копию системного пула (`SystemCertPool` + `AppendCertsFromPEM`), ставит `MinVersion: TLS1.2`. `GIGACHAT_INSECURE_SKIP_VERIFY=true` — крайний фолбэк с `log.Warn` и `//nolint:gosec`.
- **Кэш OAuth-токена.** Токен живёт 30 минут; кэшируем на `TTL` минус окно безопасности 60с, обновляем лениво под мьютексом (к боту пишут параллельно). Срок жизни считаем от момента получения (`now().Add(TTL)`), а не парсим `expires_at`: проще, детерминированно тестируется, а дрейф закрывает путь повтора на 401. `now` — поле-функция, тест управляет временем без sleep.
- **401 → ровно один повтор.** `chat` возвращает HTTP-статус отдельным значением; на 401 `Ask` принудительно переполучает токен и повторяет один раз. Второй 401 отдаётся как ошибка — без зацикливания (есть тест `TestGigaChat401NoInfiniteRetry`).
- **Таймаут.** У `http.Client` `Timeout: 0` — дедлайн держит только `context` вызывающего (45с в проде). Короткий глобальный Timeout перебил бы контекст и рвал штатную 10–20с генерацию. Тесты `TestGigaChatTimeout`/`TestYandexTimeout` проверяют, что при дедлайне контекста возвращается `context.DeadlineExceeded`.
- **YandexGPT — вторая реализация за тем же интерфейсом.** Проще: `Api-Key`, публичные CA. Ключевая ловушка вынесена в тип и комментарий: у Yandex поле сообщения — `text`, а не `content`; счётчики токенов приходят строками. `modelUri` собирается как `gpt://<folder>/<model>/latest`.
- Тела ответов читаются через `io.LimitReader(1МиБ)`; ошибки чужих ответов обрезаются `snippet` — незачем тащить в лог мегабайт HTML.
- **TODO:** сверить формат ответа OAuth (`expires_at`, единицы) и chat/усечения ошибок с офиц. документацией developers.sber.ru/docs/ru/gigachat и yandex.cloud/ru/docs/foundation-models — реальные ключи не тестировались (по условию).

## Шаг 4. knowledge: загрузка, чанкинг, отбор, лимит

- **RAG-lite без векторов.** Для FAQ/прайса одной компании эмбеддинги и векторная БД — избыточная инфраструктура. Чанкинг по markdown-заголовкам + keyword-отбор дают приемлемое качество при нулевой оснастке. Осознанный размен, зафиксирован в README.
- **Чанкинг.** `parseSections` режет файл на секции от заголовка (`#…`) до следующего. Текст до первого заголовка и файл вовсе без заголовков становятся одной безымянной секцией — терять его нельзя. Вложенные заголовки → каждый своя секция. Пустые (только пробелы) секции отбрасываются.
- **Отбор с префиксным стеммингом.** Точное совпадение подстроки промахивалось на русской морфологии («оплаты» ≠ «оплата», «картой» ≠ «карты»). Ввёл дешёвый стем — префикс в `stemLen=4` рун: сравниваем стемы слов вопроса и секции. Полноценная лемматизация не нужна для демо, а 4-символьный префикс ловит корень основных падежей. Счёт секции — число совпавших по стему слов.
- **Фолбэк.** Нет ни одного совпадения → берём первые секции файла под лимит, чтобы модель получила общий контекст о компании, а не пустоту (тест `TestSelectFallback`).
- **Лимит размера промпта.** `MaxPromptChars=12000` (~4000 токенов при оценке символы/3). `fitToLimit` набирает секции в порядке релевантности, пока укладываются; `assemble` собирает их обратно в порядке документа (читабельнее) и страхует финальным обрезанием по рунам. Если самая релевантная секция одна больше лимита — берётся и обрезается, промпт не пустой (тест `TestSelectRespectsLimit`).
- Стоп-слова (частые местоимения/предлоги) отсеиваются, иначе «как»/«для» матчили бы каждую секцию и обнуляли ранжирование.
- `Base` потокобезопасен (`sync.RWMutex`): `/reload` подменяет секции, пока параллельные запросы их читают.

## Шаг 5–8. Telegram, логирование, /reload, обработка ошибок

- **Ядро `Consultant` отделено от транспорта.** `Consultant.Answer(ctx, question)` делает всё содержательное: отбор секций, сборка системного промпта, запрос к LLM под таймаутом. Зависит от интерфейсов `LLM`/`Knowledge`, поэтому тестируется заглушками без сети и без Telegram. `Bot` — тонкая обёртка: приём апдейтов, «печатает…», отправка, запись в журнал.
- **Системный промпт** инструктирует отвечать ТОЛЬКО по базе знаний, честно признавать незнание и не выдумывать цены/сроки. Пустая база помечается явно — чтобы не выглядело, будто контекст потерялся.
- **Таймаут 45с** навешивается в `Answer` через `context.WithTimeout` поверх процессного ctx. `TestAnswerAppliesTimeout` проверяет, что отменённый родитель прерывает запрос.
- **`ChatAction "печатает…"`** перед запросом: генерация идёт 10–20с, без индикатора кажется, что бот завис.
- **Логирование диалогов best-effort.** Ошибка `SaveDialog` пишется в лог, но не отменяет уже отправленный пользователю ответ: журнал вторичен по отношению к ответу. Проверено интеграционным тестом на реальном Postgres (`TestSaveDialogIntegration`, под `TEST_DATABASE_URL`).
- **`tokens_used` — оценка (символы/3).** Интерфейс `LLMClient` намеренно узкий и точный `usage` не возвращает; реальный `total_tokens` пишется в debug-лог клиента. Для аналитики журнала грубой оценки достаточно, а колонка `tokens_used` — nullable.
- **`/reload` только для админа.** Сверяем `From.ID` с `ADMIN_TG_ID`; при пустом админе или чужом id — вежливый отказ. Неизвестные команды (`/foo`) не уходят в LLM, чтобы не жечь токены.
- **Ошибки пользователю понятны и без внутренностей.** `userFacingError` отделяет таймаут («попробуйте ещё раз») от прочей недоступности. 401 GigaChat обрабатывается ниже — внутри клиента, один повтор с новым токеном.

## Шаг 10. Сквозной graceful shutdown

- Один `signal.NotifyContext(SIGINT, SIGTERM)` создаётся в `main` и уходит во все блокирующие вызовы: миграции, пул БД, `bot.Start`, каждый запрос к LLM (как родитель 45с-дедлайна). По сигналу останова отменяется всё дерево разом; `bot.Start` возвращает управление, `store.Close()` отрабатывает через defer.
- `Bot.Run` возвращает `ctx.Err()` после остановки polling — процесс завершается штатно, а не по таймауту убийства контейнера.

## Ревью и правки (пост-аудит)

Строгое ревью выявило 9 проблем; исправлены все. Ниже — что изменилось и почему;
эти решения заменяют часть более ранних (помечено «отменяет»).

- **№1 Graceful shutdown завершался кодом 1.** `Bot.Run` возвращал `ctx.Err()` → на каждый SIGINT/`docker compose down` процесс печатал `ошибка: context canceled` и выходил с 1, а `restart: on-failure` считал это сбоем. Теперь `Run` возвращает `nil`, если ctx отменён штатно (`errors.Is(err, context.Canceled)`).
- **№2 `tokens_used` — теперь фактический usage провайдера.** *Отменяет решение Шага 3 про узкий `(string, error)`.* Интерфейс `LLMClient.Ask` возвращает `llm.Answer{Text, TokensUsed}`. Оба клиента прокидывают `usage.total_tokens` (у Yandex — из строки). Оценка символы/3 осталась только фолбэком, когда провайдер usage не вернул, и теперь считает **весь** промпт (системный + вопрос + ответ), а не только вопрос+ответ — иначе расход занижался кратно (важно для 1M-токенного freemium GigaChat).
- **№3 Срок жизни токена — по серверному `expires_at`.** *Отменяет решение Шага 3 «не парсим expires_at».* `fetchToken` читает `expires_at` (Unix-мс), срок = `min(now+30м, серверный expires_at)`. Кэш больше не переживёт реальный токен при коротком сроке/дрейфе часов; повтор на 401 остаётся страховкой.
- **№4 Лок больше не держится на время сетевого запроса.** Быстрый путь читает кэш под коротким мьютексом и отпускает его; само переполучение идёт через `singleflight.Group` — N параллельных промахов (или 401) схлопываются в один поход в OAuth. Раньше один медленный OAuth блокировал все параллельные `Ask`, включая тех, у кого валидный токен. Тест `TestGigaChatConcurrentTokenFetch` (20 горутин → 1 запрос, под `-race`).
- **№5 Добавлен `.dockerignore`.** `COPY . .` тянул в build-контекст и промежуточный слой локальный `.env` с реальными ключами, `.git`, тесты. Теперь секреты и мусор исключены. Docker build перепроверен — зелёный.
- **№6 Лимит промпта — единый источник.** `assemble` принимает `maxChars` параметром вместо хардкода `MaxPromptChars`; теперь и набор, и финальная обрезка используют одно значение (`b.maxChars`).
- **№7 Заголовки внутри code-fence не режут секцию.** `parseSections` отслеживает fenced-блоки (```` ``` ````/`~~~`); строка `# comment` в примере кода больше не создаёт фиктивную секцию. Тест добавлен.
- **№8 Секреты и DSN триммятся.** `BOT_TOKEN`, `DATABASE_URL`, `GIGACHAT_AUTH_KEY`, `YANDEX_API_KEY`, `YANDEX_FOLDER_ID` очищаются от случайных пробелов/переносов при копипасте в `.env` — иначе битый `Authorization: Basic …\n` давал невоспроизводимые 401.
- **№9 Защита границ системного промпта.** `sanitizeKnowledge` вырезает из контента базы строки, совпадающие с разделителями `=== БАЗА ЗНАНИЙ ===` / `=== КОНЕЦ … ===`, чтобы строка из FAQ не подделала границу блока и не «дописала» инструкции модели. Тест `TestSanitizeKnowledgeStripsMarkers`.
- **Проверка:** `go build`, `go vet`, `go test -race ./...`, `make lint` (0 issues), `docker build`, интеграционный тест записи в Postgres — всё зелёное после правок. `x/sync` стал прямой зависимостью (singleflight).

## Починка CI/сборки (GitHub)

- **Docker build падал «requires go >= 1.25.7».** Причина: `goose/v3@v3.27.2` в своём go.mod требует `go 1.25.7`, поэтому `go mod tidy` держит директиву модуля на `go 1.25.7`. Плавающий тег `golang:1.25-alpine` на Docker Hub мог отставать на патч (1.25.6) и не удовлетворять этому полу. Фикс: Dockerfile запинен на `golang:1.25.7-alpine` — в пару к полу go.mod (комментарий в Dockerfile объясняет связь). Пытаться опустить директиву до `go 1.25` бессмысленно: tidy её возвращает, т.к. этого требует зависимость.
- **govulncheck валил CI: `GO-2026-5970`** — бесконечный цикл на некорректном вводе в `golang.org/x/text` v0.37.0 (достижим через `sql.Open` → pgx-драйвер → `norm.Form.*`). Фикс: `x/text` поднят до v0.40.0 (фикс в v0.39.0), заодно `x/sync` до v0.22.0. Уязвимость ушла.
- **`GO-2026-5856` (crypto/tls, ECH)** — уязвимость стандартной библиотеки go1.26.4 (фикс в go1.26.5). Всплывает только локально: CI собирает на 1.25.x (setup-go `"1.25"` тянет последний пропатченный патч), поэтому там её нет. `setup-go` намеренно оставлен на `"1.25"`, а не запинен на `"1.25.7"`: плавающий минор всегда берёт свежий патч со всеми бэкпортами, а жёсткий пин мог бы, наоборот, зафиксировать непропатченную сборку и вернуть флаг. Код тут ни при чём — правится только обновлением тулчейна.
- Проверено после правок: `go build`, `go vet`, `go test -race ./...`, `make lint` (0 issues), `govulncheck` (осталась только локальная stdlib-уязвимость go1.26.4), `docker build` на `golang:1.25.7-alpine` — зелёное.

## Кворк «ИИ-бот в Telegram по базе знаний»

Репозиторий стал основой витринного кворка: бот для малого бизнеса, настройка нового клиента за часы, без правки кода. Решения ниже меняют часть более ранних — помечено «отменяет».

- **Бот ничего не хранит.** *Отменяет журнал диалогов из Шагов 5–8.* Проблема: бот писал в Postgres вопрос, ответ и `user_tg_id`, а заявки добавили бы имена и телефоны. Последствие: держатель чужих персональных данных — и на моём сервере, и на сервере клиента; каждому боту нужна своя БД. Решение: переписка, имена, телефоны и id не пишутся никуда. Недавние сообщения, шаг заявки и лимиты живут только в памяти процесса. В логах — время ответа, токены, статус, доставка владельцу, ошибки. Чем платим: у владельца нет статистики вопросов (частично закрывает режим статистики ниже), заявка теряется при падении процесса, после перезапуска бот не помнит разговор и не может переслать ответ владельца. Переписка остаётся у самого Telegram — это вне нашего контроля.
- **Утечка через ошибки Telegram.** Проблема: штатный обработчик ошибок `go-telegram/bot` при сбое разбора пишет в лог всё тело ответа (в `getUpdates` это сообщения, имена, телефоны), а сетевые ошибки содержат URL с токеном бота. Последствие: обещание «ничего не храним» нарушалось бы в `docker logs`, а токен утекал бы в лог. Решение: свой `WithErrorsHandler` и одна функция очистки для всех ошибок Telegram — токен заменяется на `***`, тело ответа вырезается. Тест `TestRedactHidesTokenAndBody`.
- **Статистика включается настройкой.** Проблема: без БД владелец не видит, о чём и сколько спрашивают; Postgres — заметная часть портфолио. Последствие: две ветки «с БД» и «без» пришлось бы править дважды. Решение: один код. Без `DATABASE_URL` бот ничего не пишет; с ним — только счётчики событий (`answer`, `not_found`, `off_topic`, `lead_sent`, `lead_failed`…) и токены, время округлено до часа. Миграция `00002` удаляет `dialogs`. Команда `/stats` показывает сводку за 7 и 30 дней. Postgres поднимается отдельным `docker-compose.stats.yml`, основной compose — один контейнер.
- **Память разговора — в процессе.** *Отменяет «бот отвечает по одному вопросу» из README.* Проблема: «а сколько это стоит?» после вопроса о съёмке модель не связывала. Решение: последние 3 пары, после 30 минут тишины разговор начинается заново. Подбор разделов базы идёт по текущему и предыдущему вопросу. Лимиты переживают сброс разговора, иначе их обходили бы паузой.
- **Статус и намерение — служебной строкой в том же ответе.** Проблема: боту нужно отличать «ответил», «частично», «нет в базе» и «не по теме», а ещё видеть желание купить. Последствие: отдельный запрос-классификатор удвоил бы расход и задержку. Решение: модель начинает ответ с `СТАТУС: …` и при явном намерении добавляет `НАМЕРЕНИЕ: ДА`; бот разбирает и вырезает метки, в том числе в markdown-обёртке. Нет метки — ответ показывается как есть и ничего не предлагается, экзамен отправляет его на ручную проверку. Отличие «нет в базе» от «не по теме» задано в промпте определением и примерами и проверяется ловушками экзамена.
- **Один механизм сбора контакта для заявки и вопроса без ответа.** Проблема: вопрос, на который нет ответа, должен дойти до владельца с контактом — по сути это заявка. Решение: одна форма с шагами «что интересует» → телефон → имя. Вход по кнопке меню начинает с интереса; предложение бота подставляет исходный вопрос; вопрос без ответа идёт в ту же форму, имя можно пропустить. «Поделиться контактом» даёт телефон и имя одним нажатием. Номер приводится к `+7…`, неправдоподобный (мало цифр, одна цифра подряд, код +7 1xx) — просьба исправить. Вопрос посреди формы бот узнаёт эвристикой («?» или больше трёх слов на шаге имени, не телефон на шаге телефона), отвечает по базе и повторяет шаг. Переходы формы — чистая функция `apply`, покрыта тестами.
- **Доставка владельцу с повторами.** Проблема: с февраля 2026 Telegram в России замедлен, сообщение владельцу может не уйти с первого раза. Решение: отправка в фоне, паузы 2с → 4с → … → 60с, окно 5 минут, у каждой попытки таймаут 20с. Человек сразу видит «Передаю…», потом подтверждение или честный отказ с контактами. При остановке по сигналу бот дожидается отправок и сразу пишет ожидающим отказ. Чем платим: при падении процесса заявка теряется, в логе остаётся только факт без данных.
- **Ответ владельца через бота.** Проблема: владельцу удобнее ответить клиенту в Telegram, чем звонить. Решение: бот помнит в памяти `id сообщения владельцу → чат клиента` 48 часов; reply владельца на заявку уходит клиенту с подписью «Вам ответил администратор». Связи нет (перезапуск, больше 48 часов) — бот честно говорит владельцу позвонить. Только текст и только в одну сторону: ответ клиента снова идёт боту как вопрос.
- **Лимиты на одного человека.** Проблема: README честно признавал, что без лимитов токены клиента выжигаются за день, а владельца можно засыпать заявками. Решение: 20 вопросов и 3 заявки в час, счётчики в памяти, значения в настройках, 0 — без лимита. Сверх лимита — ответ без запроса к модели и контакты.
- **Провайдеры с API как у OpenAI.** Проблема: опция кворка «другая нейросеть на ваш выбор». Решение: `LLM_PROVIDER=openai` + адрес, модель, ключ. Формат `/chat/completions` у GigaChat такой же, поэтому код запроса общий, у GigaChat сверху только OAuth и сертификат. *Отменяет интерфейс `Ask(ctx, systemPrompt, userMessage)`*: теперь `Ask(ctx, []Message)` ради истории, а `Answer` возвращает токены отдельно на вход и выход — у части провайдеров они стоят по-разному. HTTP-ошибки отдаются типом `StatusError{Code}`. Один повтор через 2с на сеть, 429 и 5xx живёт в ядре ответа — одинаково для всех провайдеров; на 400/401/403 повтора нет. Температура одна на всех, 0.2. В README и `.env.example` явно сказано, что с такими сервисами вопросы уходят за рубеж, а оплату клиент оформляет сам.
- **Всё, что отличается у клиентов, — в `.env`.** Проблема: новый клиент должен быть «настройки + база». Решение: название, контакты, чат владельца, тексты кнопок и подтверждений, согласие, лимиты, часовой пояс — переменные с умолчаниями, многострочный текст через `\n`. Обязательны только токен, чат владельца, название, контакты и ключ нейросети; без них бот не стартует и перечисляет всё недостающее разом. Экзамену Telegram не нужен — для него `LoadCore()`.
- **База знаний томом, а не в образе.** Проблема: `COPY knowledge/` вшивал базу в образ. Последствие: один образ на клиента, а `/reload` в Docker перечитывал неизменяемый файл. Решение: база монтируется томом (`KNOWLEDGE_DIR`), env-файл задаётся `ENV_FILE`; один образ служит всем клиентам, каждый бот — отдельный compose-проект. Том сначала был только на чтение; запись понадобилась для пополнения базы ответами владельца (ниже).
- **Утилита «файлы клиента → база знаний».** Проблема: клиенты присылают прайсы и описания в PDF, Word и таблицах. Решение: `cmd/kb` делает черновик в markdown и отчёт. DOCX и XLSX разбираются стандартной библиотекой (zip + XML): заголовки по стилям, таблицы и листы — построчно «- Услуга: …; Цена: 3 500 ₽; …», числа — как их видел клиент, с ₽ и разрядами по формату ячейки. CSV и TXT — UTF-8 или Windows-1251, в которой их сохраняет русский Excel. PDF — pdfium в WebAssembly (`go-pdfium`): ставить ничего не нужно, заголовки определяются по размеру шрифта, страницы без текста помечаются как сканы. Версия `go-pdfium` закреплена на v1.19.8: с v1.20 библиотека требует Go 1.26, а образ и CI собираются на 1.25. В отчёте — картинки, вложенные объекты, объединённые ячейки, формулы без значения; предупреждения — секции больше лимита, дубли, пустые секции, вопрос, который тянет почти весь лимит (проверяется тем же подбором, что у бота). Страница — 1 800 знаков готовой базы: не зависит от вёрстки исходников. Существующую базу утилита без `-force` не перезаписывает.
- **Экзамен перед сдачей.** Проблема: обещание «проверка до сдачи, протокол отдам вам» и «до заказа прикину расход». Решение: `cmd/exam` гоняет вопросы из CSV через то же ядро ответа, что бот, с настоящей моделью и базой, каждый вопрос без истории. Вердикт автоматический только там, где он надёжен: запрещённый факт в ответе — ошибка; статус «нет в базе» или «частично» на ловушке — честно; совпадение всех фактов после нормализации («2 500 ₽» = «2500 рублей») — по базе. Всё остальное — «проверить вручную» с пояснением; «верно» без проверки протокол не показывает. Прогон пишется в CSV с колонкой «итог» для ручного вердикта, `-report` пересобирает протокол. HTML-протокол открывается двойным кликом и на телефоне, технических деталей в нём нет. В терминале — токены вход/выход, время, стоимость ответа и месяца на 300/1 000/3 000 вопросов с учётом минимального платежа, тарифы из настроек. После правки базы видно, какие вердикты изменились с прошлого прогона.
- **`/start` и `/reload` никогда не срабатывали.** Проблема: обработчики регистрировались с шаблоном `"/start"`, а `MatchTypeCommand` в `go-telegram/bot` сравнивает команду без слэша. Последствие: на `/start` бот отвечал «Не знаю такой команды», `/reload` был недоступен — на заглушках LLM этого не видно, а живого запуска не было. Решение: шаблоны `"start"`, `"reload"`, `"stats"`. Чтобы такие ошибки маршрутизации ловились до живого теста, добавлены сквозные тесты Telegram-слоя: апдейты идут через настоящую библиотеку (`ProcessUpdate`) в поддельный сервер Telegram на `httptest` — `/start`, вопрос без ответа с передачей контакта и ответом владельца, заявка с вопросом посреди формы, не по теме и отказ, частота предложения заявки.
- **Пополнение базы ответами владельца — только с подтверждения.** Проблема: вопрос без ответа доходит до владельца, он отвечает, а в следующий раз бот снова не знает. Последствие автозаписи: ответ владельца адресован одному человеку — «Анна, для вас скидка 10%» стала бы скидкой для всех, «в эту субботу свободно» — враньём через неделю; в базу попали бы имена клиентов, а запись обошла бы вычитку и экзамен. Решение: после пересылки ответа клиенту бот показывает владельцу, что именно запишет (вопрос и ответ, без имени и телефона), с кнопками «Добавить в базу» и «Не добавлять»; reply на предложение новым текстом записывает общую формулировку вместо личной. Вопрос и ответ берутся из текста самого предложения — состояния нет, кнопка работает и после перезапуска. Запись дописывается в раздел «Ответы администратора», строки ответа не могут стать заголовками, база перечитывается сразу. Предлагается только для вопросов без ответа: ответ на заявку личный. Чем платим: том базы теперь с правом записи (на сервере — `chown 10001`), записи не проверены экзаменом до следующего прогона, дубли не сливаются — раз в пару недель их стоит разнести по секциям руками. Сквозные тесты: добавить, переформулировать, не добавлять, ответ на заявку без предложения.
